# Outage data

This is the piece that varies most. Many utilities block cross-origin requests from other websites, so `.github/workflows/outages.yml` fetches the utility's public data server-side with `scripts/fetch_outages.py` and commits `data/outages.json` for the page to read (the "git scraping" pattern); it then starts the Pages deploy so the site picks up the new numbers. The schedule is **commented out** in the template: uncomment the `cron` line once your provider and secret are set (until then the workflow exits in seconds).

- **Kubra Storm Center** utilities usually allow direct browser requests (look for `kubra.io/stormcenter/api` in your browser's dev tools on the outage map page). You may be able to skip the workflow and change `loadOutages()` in `app.js` to fetch directly.
- **Avangrid-family utilities** (the response shape `fetch_outages.py` understands): set `outages.provider` to `"avangrid"`, set `api_url`, `api_key_header`, `match_town`, and `match_county`, and add the public subscription key from your utility's outage-map request headers as a repository secret named `OUTAGE_API_KEY` (**Settings, Secrets and variables, Actions**). `town.json` stores only the *name* of the environment variable (`api_key_env`), never the key. If you rename it, update the `env:` line in `outages.yml` to match.
- **Anything else**: set `outages.provider` to `"none"` and rely on the link-out buttons (`report_url`, `map_url`). A reliable button beats a broken widget. The page shows a "data unavailable" message with the buttons if the data file is missing.

`data/outages.json` in this repo is a fictional sample marked `"sample": true`; the page ignores it. With provider `"none"` or no secret, the workflow does nothing and the Power section shows link-outs and "Unavailable" instead of numbers.

How the page treats the data: it is shown only if the file has the expected shape, is not a sample, and was fetched within `outages.stale_after_minutes` (default 90); otherwise the Power tile says "Unavailable". The fetch script rejects a malformed API response and keeps the last good file (the run fails visibly), and rewrites the file only when the numbers change or every ~45 minutes, to keep the commit history small. If the utility is reporting other towns but none matches `match_town`, the fetch **fails** (and writes nothing) so a typo cannot pass as "no outages"; the page likewise says "No data for <town> (check match_town)". Run `OUTAGE_API_KEY=... python3 scripts/fetch_outages.py --towns` to see how the utility spells names, fix `match_town`, and once you are sure of the spelling set `outages.match_verified` to `true` (after that, a missing row means "no outages in your town"). Numbers must be whole and non-negative, and timestamps cannot be in the future, or the data is rejected. "No data" is also shown when the utility reports outages overall but lists no towns at all, because then a missing row proves nothing.

**Frozen feeds and time zones.** The page and the script check two ages: when *we* last fetched the file (`stale_after_minutes`, default 90) and when the *utility's own* `lastUpdated` says its data was produced (`max_source_age_minutes`, default 360). A utility feed that has stopped updating, behind a fresh fetch, therefore shows "Unavailable" rather than "No outages". The utility writes `lastUpdated` as local time with no zone, so it is read in `location.timezone` (an IANA name such as `America/Chicago`); if that is missing or invalid, the timestamp is in an unrecognised format, the date or time does not exist (minute 60, February 30, or a clock time skipped when clocks jump forward), or an explicit offset is outside +-14:00, the data is treated as unverifiable and shown as unavailable. A clock time that happens twice when clocks go back is read as the first one. A limit of zero or less is ignored and the default is used. `outages.data_file` must be a file inside `data/`: the page, the fetch script and `check-config` all refuse anything else.

The workflow commits to and starts the Pages deploy from your default branch (`main`), so main must accept pushes from the `github-actions` bot (no blocking branch protection), and Pages must already be enabled.

## Maintenance

- GitHub pauses cron workflows after ~60 days of repo inactivity. The outage bot's commits normally keep it alive; if the Power section says "Unavailable", re-enable the workflow under the Actions tab.
- If the utility rotates its public API key, or changes its response format, the fetch run fails (you will see it in the Actions tab) and the page shows "Unavailable" once the last good data is older than `stale_after_minutes`, rather than presenting old numbers as current. Update the repository secret or `fetch_outages.py`.
